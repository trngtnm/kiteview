# Implementation Plan: KiteView

**Product name:** KiteView
**Document version:** 1.0
**Date:** September 18, 2026

---

## 1. Executive Summary

KiteView is a cross-platform document reader that turns static PDFs — including scanned documents — into an interactive, personalized reading experience. Users can tap or highlight any word or phrase to get instant definitions, paraphrases, and contextual annotations generated by a combination of dictionary APIs and an LLM (ChatGPT API). The system learns from a user's stated reading preferences and reading history to tailor the complexity and style of explanations. It also detects fillable form fields in PDFs, visually indicates blank fields, and can auto-fill them using data from the user's profile.

The application is built once in React Native to ship to iOS, Android, and macOS (via **react-native-macos**, a true native macOS app rather than a browser-wrapped shell), with a React Native Web build for a future full web app — all sharing a single codebase. Supabase provides authentication, database, storage, and edge functions for the backend.

---

## 2. Goals & Non-Goals

### 2.1 Goals
- Render both digital-native and scanned PDFs accurately across platforms.
- Let users select any word/phrase and receive a definition, simplified paraphrase, or contextual explanation.
- Personalize annotation complexity/style based on a stored reading-preference profile (e.g., reading level, native language, domain expertise, preferred tone).
- Detect and visually highlight PDF form fields (blank inputs) and offer AI-assisted autofill from profile data.
- Allow users to save, edit, and export their annotations (as a new PDF, markdown, or standalone notes file).
- Provide a PDF converter (e.g., DOCX/image/HTML → PDF, and PDF → editable formats).
- Let users create, store, and apply a signature (drawn, typed, or uploaded) to sign detected signature fields on forms.
- Support offline reading with sync when reconnected.

### 2.2 Non-Goals (v1)
- Full collaborative/multi-user real-time annotation (co-editing) — deferred to a later phase.
- OCR training / custom OCR model development — use a managed OCR service instead.
- Legally-binding e-signature workflows requiring identity verification, audit trails, or compliance certification (e.g., ESIGN/UETA-grade certified signing, notarization, multi-party signing ceremonies) — v1 supports self-signing of forms for personal/practical use, not a certified e-signature product like DocuSign.

## 3. Target Users & Core Use Cases

| Persona | Need | How the product helps |
|---|---|---|
| Language learner | Encounters unfamiliar vocabulary in foreign-language PDFs | Tap-to-define with translations tuned to their proficiency level |
| Student / researcher | Reads dense academic papers | Paraphrasing of jargon at a chosen reading level, saved annotations for study |
| Professional filling forms | Receives scanned PDF forms (contracts, applications) | Field detection + autofill from saved profile data, plus one-tap signing of signature fields |
| Accessibility-focused reader | Needs simplified language | Adjustable "explain like I'm..." complexity slider tied to profile |
| Knowledge worker | Needs to convert/export documents | PDF converter and export-to-notes features |

## 5. Core Feature Breakdown

### 5.1 PDF Rendering Engine

- **Digital PDFs:** Use `react-native-pdf` (mobile) backed by `pdfium`, and `pdf.js` for the web/desktop builds, wrapped behind a shared `pdf-engine` interface so upstream code doesn't care which renderer is active.
- **Scanned PDFs:** Detected by checking whether extractable text layers exist (via `pdf.js`'s text content API). If a page has no text layer:
  1. Rasterize the page to an image.
  2. Send the image to a managed OCR service (Google Cloud Vision or AWS Textract) via an Edge Function.
  3. Store the returned text + bounding-box coordinates alongside the page, creating an invisible, positioned text layer overlaid on the scanned image so selection/highlighting works identically to native text PDFs.
- OCR results are cached in Supabase (per file hash) so re-opening a previously processed scan doesn't re-run OCR.

### 5.2 Word/Phrase Lookup & AI Annotation

**Flow when a user taps or highlights text:**

1. Client captures selected text + surrounding paragraph (for context) + page number + bounding box.
2. Client calls a Supabase Edge Function (`/annotate`) with: selected text, context window, and the user's `reading_profile_id`.
3. Edge Function:
   - Checks a `definitions_cache` table keyed by `(term, source_language, reading_level_bucket)` to avoid duplicate LLM calls.
   - If not cached, queries a **dictionary API** (e.g., Merriam-Webster API, Wordnik, or Free Dictionary API) for a baseline definition.
   - Passes the term, baseline definition, and surrounding context to the **LLM API** with a system prompt that incorporates the user's reading profile (see 5.3) to produce a tailored explanation/paraphrase.
   - Persists the result to `definitions_cache` and to the user's `annotations` table (linked to the specific document + selection coordinates).
4. Client renders the annotation in a popover/side panel, with options to save, edit, delete, or regenerate.

**Annotation types supported:**
- Dictionary definition (literal)
- Simplified paraphrase (reading-level adjusted)
- Contextual explanation ("what this means in this sentence")
- Translation (if user's profile indicates a non-native language)
- User's own free-text note

### 5.3 Reading Preference Profile & Personalization

Captured at onboarding and editable anytime in Settings:

- Reading level (e.g., grade-school, general adult, advanced/academic)
- Native language / preferred explanation language
- Domain familiarity tags (legal, medical, technical, financial, literary)
- Tone preference (concise vs. conversational vs. formal)
- Vocabulary difficulty threshold (auto-annotate words above X frequency-rank automatically, without the user needing to tap them)
- Autofill profile data (name, address, DOB, etc. — used only for form autofill, stored separately with stricter access controls)

This profile is passed as structured metadata into the LLM system prompt for every annotation request, ensuring consistent tailoring. The profile is versioned so that regenerating an old annotation reflects current preferences on demand while past annotations remain unchanged unless explicitly refreshed.

### 5.4 Form Field Detection & Autofill

- Use the PDF's native AcroForm field data when present (via `pdf-lib` or `pdfium` bindings) to detect field type, name, and position.
- For scanned forms without embedded field metadata, use a layout-analysis pass (OCR bounding boxes + heuristics, optionally an LLM vision call) to infer likely blank fields (e.g., underscores, boxes, lines) and label them semantically ("Full Name", "Date", "Signature").
- Detected fields are rendered as visually distinct overlays (dashed outline + label chip) directly on the page.
- **Autofill:** a button per field or a "Fill All" action maps detected field semantics to the user's stored profile fields via a matching function (exact key match → fuzzy/LLM-assisted match for ambiguous labels), then writes values into an editable overlay layer (never altering the original PDF bytes until export).
- All autofilled values remain editable before the user finalizes/exports.

### 5.5 Signature Feature

- **Signature creation:** users create one or more signatures in Settings via:
  - **Draw** — freehand drawing captured with a touch/trackpad/mouse canvas (`react-native-svg` or a canvas-based signature pad component), saved as a vector path (SVG) so it scales cleanly at any size.
  - **Type** — user types their name and picks from a small set of script/handwriting-style fonts, rendered to an image/SVG.
  - **Upload** — user uploads a photo of their physical signature; the image is auto-cropped and background-removed (transparent PNG) via a simple thresholding step (client-side or a lightweight Edge Function).
- Users can save multiple named signatures (e.g., "Full signature", "Initials") and set a default.
- **Applying a signature:** when the form-detection pass (5.6) identifies a signature field, it's rendered as a tappable placeholder ("Tap to sign"). Tapping opens the saved signature picker (or the draw/type/upload flow for a first-time signature) and places the chosen signature image into the field's bounding box as an editable, resizable/movable overlay layer — the underlying PDF bytes aren't modified until export.
- **Initials fields:** detected separately from full-signature fields (via label heuristics, e.g., "Initial here") and auto-suggest the user's saved initials signature.
- **Storage:** signature images/SVGs are stored in a private Supabase Storage bucket, referenced from a `signatures` table (see §7), scoped by RLS to the owning user. Because a signature image is sensitive personal data, it is never sent to the LLM or dictionary APIs and is excluded from any analytics/logging.
- **Multi-signature documents:** a document can track multiple signature fields (e.g., signer + witness) if the user is filling out a form on someone else's behalf is out of scope for v1 — v1 assumes one signer applying their own signature(s) to their own copy of a document.
- Explicitly **not** included in v1 (see §2.2 Non-Goals): certified/audit-trail e-signature workflows, multi-party remote signing invitations, or identity verification — this is a personal "sign my own form" convenience feature, not a DocuSign-style product.

### 5.6 Form Field Detection & Autofill

- Use the PDF's native AcroForm field data when present (via `pdf-lib` or `pdfium` bindings) to detect field type, name, and position — including native `/Sig` signature field types, which route directly into the signature flow above.
- For scanned forms without embedded field metadata, use a layout-analysis pass (OCR bounding boxes + heuristics, optionally an LLM vision call) to infer likely blank fields (e.g., underscores, boxes, lines) and label them semantically ("Full Name", "Date", "Signature", "Initials").
- Detected fields are rendered as visually distinct overlays (dashed outline + label chip) directly on the page.
- **Autofill:** a button per field or a "Fill All" action maps detected field semantics to the user's stored profile fields via a matching function (exact key match → fuzzy/LLM-assisted match for ambiguous labels), then writes values into an editable overlay layer (never altering the original PDF bytes until export). Signature/initials fields are matched to the signature flow rather than plain text autofill.
- All autofilled and signed values remain editable/replaceable before the user finalizes/exports.

### 5.7 Export Feature

Supported export targets:
- **Annotated & signed PDF** — flattens the original PDF with annotation highlights, margin notes, filled form fields, and applied signatures baked in (via `pdf-lib`).
- **Notes export** — Markdown or DOCX file containing just the saved annotations, organized by page/section.
- **Data export** — JSON of all annotations/highlights for backup or use in other tools.

### 5.8 PDF Converter

- **Into PDF:** DOCX, images (JPG/PNG), and plain text → PDF (server-side conversion via an Edge Function calling a conversion library, e.g., LibreOffice headless or a hosted conversion API).
- **From PDF:** PDF → DOCX (editable) and PDF → plain text, useful after OCR has extracted a text layer from scans.
- Conversion jobs run asynchronously; the client polls or subscribes (via Supabase Realtime) for job completion status.

## 7. Data Model (Supabase / Postgres)

```sql
-- Users are managed by Supabase Auth (auth.users); the following extend it.

create table profiles (
  id uuid primary key references auth.users(id) on delete cascade,
  display_name text,
  created_at timestamptz default now()
);

create table reading_preferences (
  id uuid primary key default gen_random_uuid(),
  user_id uuid references profiles(id) on delete cascade,
  reading_level text check (reading_level in ('beginner','intermediate','advanced','academic')),
  native_language text,
  explanation_language text,
  domain_tags text[],           -- e.g. {'legal','medical'}
  tone text check (tone in ('concise','conversational','formal')),
  auto_annotate_threshold numeric,  -- frequency-rank cutoff
  updated_at timestamptz default now()
);

create table autofill_profile (
  id uuid primary key default gen_random_uuid(),
  user_id uuid references profiles(id) on delete cascade,
  field_key text,                -- e.g. 'full_name', 'address_line_1'
  field_value text,              -- encrypted at rest
  updated_at timestamptz default now()
);

create table documents (
  id uuid primary key default gen_random_uuid(),
  user_id uuid references profiles(id) on delete cascade,
  storage_path text not null,
  original_filename text,
  page_count int,
  is_scanned boolean default false,
  ocr_status text check (ocr_status in ('none','pending','complete','failed')),
  file_hash text,                -- for dedupe/caching
  created_at timestamptz default now()
);

create table document_pages (
  id uuid primary key default gen_random_uuid(),
  document_id uuid references documents(id) on delete cascade,
  page_number int,
  ocr_text jsonb,                -- text blocks + bounding boxes
  detected_fields jsonb          -- form field metadata
);

create table annotations (
  id uuid primary key default gen_random_uuid(),
  document_id uuid references documents(id) on delete cascade,
  user_id uuid references profiles(id) on delete cascade,
  page_number int,
  selection_text text,
  bounding_box jsonb,
  annotation_type text check (annotation_type in ('definition','paraphrase','context','translation','note')),
  content text,
  reading_profile_snapshot jsonb, -- profile state at time of generation
  created_at timestamptz default now()
);

create table definitions_cache (
  id uuid primary key default gen_random_uuid(),
  term text,
  source_language text,
  reading_level_bucket text,
  dictionary_result jsonb,
  llm_result text,
  created_at timestamptz default now(),
  unique (term, source_language, reading_level_bucket)
);

create table signatures (
  id uuid primary key default gen_random_uuid(),
  user_id uuid references profiles(id) on delete cascade,
  label text,                    -- e.g. 'Full signature', 'Initials'
  source_type text check (source_type in ('drawn','typed','uploaded')),
  storage_path text not null,    -- SVG or transparent PNG in private bucket
  is_default boolean default false,
  created_at timestamptz default now()
);

create table document_signatures (
  id uuid primary key default gen_random_uuid(),
  document_id uuid references documents(id) on delete cascade,
  signature_id uuid references signatures(id) on delete set null,
  page_number int,
  bounding_box jsonb,
  applied_at timestamptz default now()
);

create table conversion_jobs (
  id uuid primary key default gen_random_uuid(),
  user_id uuid references profiles(id) on delete cascade,
  source_format text,
  target_format text,
  source_path text,
  result_path text,
  status text check (status in ('queued','processing','complete','failed')),
  created_at timestamptz default now()
);
```

**Row Level Security (RLS):** every user-owned table (`documents`, `annotations`, `reading_preferences`, `autofill_profile`, `signatures`, `conversion_jobs`) enforces `user_id = auth.uid()` policies for select/insert/update/delete. `document_signatures` inherits access via a join to `documents.user_id`. `definitions_cache` is shared/read-only to all authenticated users (no PII).

Sensitive fields in `autofill_profile` (e.g., addresses, ID numbers) should be encrypted at the application layer (e.g., via `pgcrypto` or client-side encryption before storage) given their sensitivity.

## 8. API / Edge Function Design

| Endpoint (Edge Function) | Purpose |
|---|---|
| `POST /ocr/process` | Triggers OCR on an uploaded scanned PDF; writes results to `document_pages` |
| `POST /annotate` | Given selected text + context + profile, returns tailored annotation (checks cache → dictionary API → LLM) |
| `POST /forms/detect` | Analyzes a document's pages for fillable/blank fields |
| `POST /forms/autofill` | Maps detected fields to `autofill_profile` values |
| `POST /signatures` | Saves a new signature (drawn/typed/uploaded) to storage + `signatures` table |
| `POST /documents/:id/sign` | Applies a saved signature to a detected field on a document (writes `document_signatures`) |
| `POST /export` | Generates an exported file (annotated + signed PDF, notes doc, JSON) and returns a signed URL |
| `POST /convert` | Queues a format conversion job |
| `GET /jobs/:id` | Polls job status (or use Supabase Realtime channel instead) |

All endpoints validate the Supabase JWT, enforce per-user rate limits, and log usage for cost monitoring (LLM/OCR calls are the primary variable cost driver).

## 9. Security & Privacy Considerations

- All third-party API keys (LLM, dictionary, OCR) stored as Supabase secrets, accessed only from Edge Functions.
- PDFs and exports stored in private Supabase Storage buckets with signed, time-limited URLs.
- Autofill profile data (potentially PII) encrypted at rest; access scoped strictly via RLS.
- Signature images/SVGs are biometric-adjacent personal data: stored only in private, per-user storage paths, never shared across users, never sent to any dictionary/LLM API, and excluded from analytics or crash-report payloads.
- Explicit user consent flow before enabling autofill with personal data.
- On macOS, offer Touch ID / password gating (via `LocalAuthentication`-equivalent bridging) before revealing or applying a saved signature, as an extra safeguard against unauthorized use on a shared machine.
- Data retention/deletion: users can delete their account, which cascades to remove documents, annotations, and profile data (Postgres `on delete cascade`).
- Rate limiting and abuse detection on LLM/OCR endpoints to control cost and prevent misuse.
- Compliance considerations: depending on target markets, plan for GDPR (EU) and CCPA (California) data-subject rights (export/delete).

## 10. Non-Functional Requirements

- **Performance:** PDF pages should render within ~300ms on modern devices; annotation lookups should return within ~2s (cache hits should be near-instant).
- **Offline support:** Previously opened documents and their annotations are cached locally (SQLite via `expo-sqlite` or WatermelonDB) and sync to Supabase when connectivity returns.
- **Scalability:** Definitions cache reduces redundant LLM calls; OCR results cached per file hash to avoid reprocessing identical documents.
- **Accessibility:** Screen-reader support, adjustable font sizes, high-contrast mode.
- **Cross-platform consistency:** Shared `pdf-engine` and `ui` packages minimize platform-specific divergence in look/behavior.

## 13. CI/CD & Release Pipeline

### 13.1 Source Control & Branching
- **Trunk-based development** on a monorepo (`main` branch), with short-lived feature branches merged via PR.
- Conventional commits (`feat:`, `fix:`, `chore:`, etc.) to drive automated changelog generation and semantic versioning (via **Changesets**, which works well in a Turborepo/Nx monorepo with independently versioned `apps/*`).
- Branch protection on `main`: required PR review, required status checks (lint, typecheck, unit tests) before merge.

### 13.2 CI Orchestration
- **GitHub Actions** as the primary CI runner, with **Turborepo remote caching** (Vercel Remote Cache or self-hosted) so CI only rebuilds/retests packages actually affected by a given PR's changes — critical in a monorepo with three app targets.
- A single reusable `ci.yml` workflow triggered on every PR and push to `main`:
  1. Install deps (cached via `actions/cache` keyed on lockfile hash).
  2. Lint (ESLint) + type-check (`tsc --noEmit`) across all packages.
  3. Unit tests (Jest) with coverage upload (Codecov).
  4. Turborepo determines which of `apps/mobile`, `apps/macos`, `apps/web`, `packages/*` were affected and only runs their build/test targets.

### 13.3 Mobile (iOS/Android) Pipeline
- **EAS Build** (Expo Application Services) for cloud-based iOS/Android builds — avoids needing to maintain macOS runners solely for iOS builds, and handles code signing credential management.
- **EAS Submit** to push builds to TestFlight (iOS) and the Google Play internal/closed testing track (Android) automatically on merge to `main` or on a tagged release.
- **EAS Update** (OTA updates) for JS-only changes between native builds, gated behind a "release channel" (e.g., `preview`, `production`) so QA and staged rollouts don't require a full app-store review cycle.
- Pipeline: PR → CI checks pass → merge to `main` → nightly/on-tag `eas build --platform all --profile preview` → internal QA → on release tag, `eas build --profile production` + `eas submit`.

### 13.4 macOS (`react-native-macos`) Pipeline
- Requires a **macOS GitHub Actions runner** (`macos-latest`) since Xcode is needed to build the native app.
- **Fastlane** (`fastlane/Fastfile`) to standardize: version bump → `xcodebuild` archive → code signing (via `match` for shared certificates/provisioning profiles stored encrypted in a private repo or cloud storage) → notarization (`notarytool`) → packaging as a signed `.dmg` or `.pkg`.
- Distribution decision needed (see Open Questions): Mac App Store submission (via Fastlane `deliver`) vs. direct/self-hosted distribution with a Sparkle-style auto-updater. Both can be scripted in the same Fastlane lane, gated by a `RELEASE_CHANNEL` flag.
- Because macOS builds are slower and runner-constrained, they run on merge-to-`main` and on release tags, not on every PR — PRs affecting `apps/macos` instead run a faster "build only, no sign/notarize" smoke check.

### 13.5 Web (Future Phase) Pipeline
- Standard SPA deploy: GitHub Actions builds the React Native Web bundle, deploys to **Vercel** or **Netlify**.
- **Automatic PR preview deployments** so reviewers can click through UI changes before merging.
- Production deploy triggered on merge to `main` (or a release tag, once the web app is out of preview).

### 13.6 Supabase (Backend) Pipeline
- Supabase schema and Edge Functions are treated as code, versioned in `supabase/migrations/` and `supabase/functions/`.
- A dedicated workflow (`supabase-deploy.yml`) runs on changes to the `supabase/` directory:
  1. `supabase db lint` / `supabase db diff --linked` against a staging project to catch destructive or unintended schema drift.
  2. `supabase db push` (migrations) and `supabase functions deploy` to a **staging** Supabase project on merge to `main`.
  3. A manual approval gate (GitHub Environments "production" protection rule) before the same migration/function set is promoted to the **production** Supabase project.
- Three Supabase environments recommended: **local** (Supabase CLI + Docker for development), **staging**, and **production** — each with its own project ref, API keys, and secrets.

### 13.7 Environments & Secrets
- Environment-specific config (Supabase URL/anon key, LLM/dictionary/OCR API keys, feature flags) managed via GitHub Actions **Environments** (`staging`, `production`) with scoped secrets — never committed to the repo.
- LLM, dictionary, and OCR API keys live only in Supabase Edge Function secrets (`supabase secrets set`) and CI deploy credentials — never in client-side env files, consistent with §9's security requirements.
- Consider a secrets manager (e.g., Doppler or 1Password Secrets Automation) if the number of environments/services grows, to avoid secret sprawl across GitHub, EAS, and Supabase dashboards.

### 13.8 Release Process Summary

| Trigger | Action |
|---|---|
| PR opened | Lint, typecheck, unit tests, affected-package builds (Turborepo), macOS smoke build (no signing) |
| Merge to `main` | Deploy Supabase migrations/functions to **staging**; EAS `preview` build; web preview deploy |
| Manual approval | Promote Supabase changes to **production** |
| Release tag (e.g., `v1.2.0`) | EAS `production` build + submit (iOS/Android); Fastlane macOS signed/notarized build + distribution; web production deploy; Changesets-generated changelog published |

### 13.9 Monitoring the Pipeline Itself
- Sentry release tracking tied to each build's version/commit SHA, so crashes can be attributed to a specific release across all three platforms.
- Slack/GitHub notifications on build or deploy failure, especially for the Supabase production-promotion step given its higher blast radius.

## 14. Testing Strategy

- **Unit tests:** business logic in `packages/core` (Jest).
- **Component tests:** shared UI components (React Native Testing Library).
- **E2E tests:** Detox (mobile and macOS, via `react-native-macos` Detox support), Playwright (future web app).
- **Signature flow QA:** manual and automated checks that drawn/typed/uploaded signatures render correctly at multiple sizes/resolutions and survive PDF flattening on export.
- **Manual QA matrix:** cross-platform rendering checks for a curated set of representative PDFs (native text, scanned, forms, mixed-content, right-to-left languages).
- **LLM output review:** a sampling/evaluation process to periodically check annotation quality and appropriateness across reading levels.
